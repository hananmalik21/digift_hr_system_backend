# Application Match APIs

Deterministic 0–100 match scoring for candidates who have applied to a requisition. Scores are not generated by an LLM.

Canonical routes follow existing DigifyHR prefixes. Spec `/api/recruiting/...` aliases are also mounted.

| Method | Path |
| ------ | ---- |
| GET | `/api/recruitment/requisitions/:requisition_guid/application-matches` |
| GET | `/api/recruitment/applications/:application_guid/match` |
| POST | `/api/recruitment/applications/:application_guid/recalculate-match` |
| POST | `/api/recruitment/requisitions/:requisition_guid/recalculate-application-matches` |
| GET | `/api/recruitment/requisitions/:requisition_guid/application-match-summary` |

Also mounted at `/api/rec/requisitions/...` and `/api/recruiting/...`.

Enterprise ID is taken from hostname / JWT. Do not send `enterprise_id` as trusted security context.

## cURL

```bash
TOKEN=...
BASE=http://localhost:3000
REQ=574176DB57C7EFCBE0631718000A61BB
APP=APPLICATION_GUID

# API 1 — list
curl -sS -H "Authorization: Bearer $TOKEN" \
  "$BASE/api/recruitment/requisitions/$REQ/application-matches?page=1&page_size=20&min_match_score=70&eligibility_status=ELIGIBLE&sort_by=match_score&sort_order=desc"

# API 2 — detail
curl -sS -H "Authorization: Bearer $TOKEN" \
  "$BASE/api/recruitment/applications/$APP/match"

# API 3 — recalculate one
curl -sS -X POST -H "Authorization: Bearer $TOKEN" \
  "$BASE/api/recruitment/applications/$APP/recalculate-match"

# API 4 — recalculate all (chunked, 25 applications per round-trip)
curl -sS -X POST -H "Authorization: Bearer $TOKEN" \
  "$BASE/api/recruitment/requisitions/$REQ/recalculate-application-matches"

# API 5 — summary
curl -sS -H "Authorization: Bearer $TOKEN" \
  "$BASE/api/recruitment/requisitions/$REQ/application-match-summary"
```

### API 2 — 200 (detail excerpt)

Score breakdown, `matched_requirements`, `missing_requirements` (status `MATCHED` | `NOT_MATCHED` | `UNKNOWN`), `missing_data`, and component objects (`skills`, `experience`, `qualification`, `title`, `job_family`, `screening`, `availability`, `location`, `compensation`). `profile_completeness` is informational and is **not** in the 0–100 match score.

## Error responses

| HTTP | When |
| ---- | ---- |
| 400 | Invalid GUID, page, `min_match_score`, `match_level`, `eligibility_status`, `application_stage`, `sort_by` |
| 401 | Missing/invalid auth (existing `requireAuth`) |
| 403 | Hostname/JWT enterprise does not match a supplied `enterprise_id` |
| 404 | `{ "success": false, "message": "Requisition does not exist." }` or `Application does not exist.` |
| 500 | Unexpected Oracle/Node error (generic message, no stack) |

List query parameters: `page`, `page_size` (default 20, max 100), `min_match_score`, `match_level`, `eligibility_status`, `application_stage`, `sort_by`, `sort_order`, `search`.

Default sort: `MATCH_SCORE DESC`, `APPLIED_DATE ASC`.

## Score model

```
MATCH_SCORE =
  skills×0.30 + experience×0.20 + qualification×0.15 + title×0.10
  + job_family_level×0.10 + screening×0.05 + availability×0.04
  + location×0.03 + compensation×0.03
```

Rounded to a whole number for display. Unknown components use 50 (not a confirmed mismatch).

## Assumptions (tables/columns not in the current REC implementation)

1. **No `REC.CANDIDATE_SKILLS` table.** Skills are taken from `CANDIDATE_ASSESSMENTS.skills_json` (structured) and, only when no structured skills exist, from experience titles/descriptions.
2. **No screening / knockout question tables.** `screening_score` is 50 (`UNKNOWN`) with `knockout_failed: false` and `missing_data` includes `Application screening responses`. The scorer accepts a `screening.questions/answers` payload if those tables are added later.
3. **Candidates have no `JOB_FAMILY_ID` / `JOB_LEVEL_ID`.** Family/level scores use requisition objects plus title similarity to job-family name; otherwise 50 + `missing_data`.
4. **No currency conversion service.** Different `SALARY_CURRENCY` vs requisition `currency_code` → `compensation_status: NOT_COMPARABLE`, score 50.
5. **No persist table required.** List, detail, and summary compute scores live from `REC.V_APPLICATIONS` + `REC.CANDIDATES_FULL_V` + `REC.V_REQUISITION_LIST`. POST recalculate returns the same live scores; persist is skipped if `REC.REC_APPLICATION_MATCHES` is not present.
6. **Requisition `skills_json` shape is not documented in Node.** The scorer accepts strings or objects with `skill_name` / `skill` / `name`, `required_flag` / `required` / `skill_type` (`REQUIRED` vs `PREFERRED`), optional `years` and `proficiency`.
7. **Experience bands** prefer `REC.REC_LOOKUP_VALUES` meaning/description for `experience_required_code`. Fallback codes: `ENTRY_0_2`, `MID_3_5`, `SENIOR_5_8`, `LEAD_8_PLUS`, plus existing candidate-filter codes `EXP_0_2`, `EXP_3_5`, `EXP_6_10`, `EXP_10_PLUS`.
8. **Location** compares `CANDIDATES.CURRENT_LOCATION` (string) to `FNDSEC.FNDSEC_WORK_LOCATIONS_V.LOCATION_NAME` resolved from requisition `primary_location_id`. Candidates have no `preferred_work_mode`.
9. **`application_stage`** maps to `V_APPLICATIONS.CURRENT_STAGE_CODE` (`APPLIED`, `SCREENING`, …), not a `NEW` code.
10. **Required certifications** are a VARCHAR2 on the requisition (`required_certifications`), treated as mandatory when present and confirmed missing.
